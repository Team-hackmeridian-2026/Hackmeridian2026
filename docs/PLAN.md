# BioLicensing — Development plan

> Team: FASSINOU Aziz · CHAFI Marwane · Antoine
> Deadline: HackMeridian, Lisbon, 25–26 October 2026
> Written on 22 October 2026

This document describes everything to build, in which order, and what must be
"done" at each step. We only start coding once the team has approved this plan.

---

## 1. MVP goal

An **end-to-end demo on the Stellar testnet**, playable in 3 minutes in front of
the jury:

1. A researcher lists a patent → a **licence IP-NFT** is minted.
2. A fund commits **EURC** into a **3-milestone escrow** → it receives **shares**.
3. The lab submits the proof of milestone 1 → **challenge window**.
4. No dispute → the EURC instalment is **released automatically** to the lab.
5. An industrial licensee pays a **royalty** → it is **split** between the
   university, the inventors and the shareholders, who **withdraw** it when they want.

Every step must be visible on `stellar.expert` (testnet).

**Out of the MVP scope** (mentioned in the pitch as the roadmap): mainnet, real
KYC (SEP-12), SEPA anchors (SEP-24), secondary market for shares, security audit.

```
      │ licences + NDA   │ │ EURC + milestones│ │ shares + royalties│
      └──────────────────┘ └────────┬─────────┘ └───────┬──────────┘
                                    │                   │
                          ┌─────────▼───────────────────▼─────────┐
                          │ EURC (Stellar Asset Contract, SAC)    │
                          └───────────────────────────────────────┘
Scientific dossier files: SHA-256 hash computed in the browser
(+ optional encrypted upload to IPFS).
```

**Key decisions**

| Decision | Choice | Why |
|---|---|---|
| One instance per contract or per licence? | **One instance per contract**, data keyed by `license_id` | A single deployment, simpler front-end |
| Backend? | **None** for the MVP: the front-end reads contract state through RPC | Less code, fewer failures during the demo |
| Share token | **Built into `royalty_splitter`** (SEP-41-like interface: `balance`, `transfer`) with a **KYC allowlist** and admin **clawback** | Pro-rata royalty sharing requires the contract to see every transfer (see §3.3). A classic asset does not allow that |
| EURC | Circle's official EURC on testnet if available; otherwise a test `EURC` asset issued by us and wrapped in a SAC | The demo must not depend on an external faucet |
| Arbitration | "Arbiter" address set when the project is created | Simple, easy to explain, consistent with the pitch |

> ⚠️ Pitch / code alignment: the "shares" slide must say "Soroban share token
> with a KYC allowlist and clawback, on the model of Stellar's regulated
> assets", not "classic Stellar asset".

## 3. Contract specification (Rust, `soroban-sdk`)

Conventions: amounts in `i128` (7 decimals like EURC), percentages in **basis
points** (`bps`, 10,000 = 100 %), durations in seconds, timestamps from
`env.ledger().timestamp()`. Every action emits an **event** (the front-end and
the demo use them).

### 3.1 `ip_license_nft`

Storage: `Admin`, `NextId`, `Institution(Address) -> bool`,
`License(u64) -> License`, `NdaSigned(u64, Address) -> u64 (timestamp)`.

```rust
struct LicenseTerms { exclusive: bool, territory: String, field: String, duration_years: u32 }
struct License {
    id: u64, owner: Address /* university / lab */, title: String,
    inventors: Vec<Address>, terms: LicenseTerms,
    dossier_hash: BytesN<32>, metadata_uri: String, created_at: u64,
}

fn __constructor(env, admin: Address)
fn register_institution(env, institution: Address)          // admin
fn mint(env, owner: Address, title: String, inventors: Vec<Address>,
        terms: LicenseTerms, dossier_hash: BytesN<32>, metadata_uri: String) -> u64  // owner.require_auth + verified institution
fn get_license(env, id: u64) -> License
fn list_licenses(env, start: u64, limit: u32) -> Vec<License>
fn owner_of(env, id: u64) -> Address
fn transfer(env, id: u64, from: Address, to: Address)      // from.require_auth; to must be an institution
fn sign_nda(env, id: u64, viewer: Address)                  // viewer.require_auth; records access to the dossier on-chain
fn has_signed_nda(env, id: u64, viewer: Address) -> bool
```

Events: `minted`, `transferred`, `nda_signed`.

### 3.2 `milestone_escrow`

Storage: `Admin`, `Token` (EURC), `Splitter` (address of `royalty_splitter`),
`Treasury`, `FeeBps`, `NextId`, `Project(u64) -> Project`.

```rust
enum MilestoneStatus { Pending, Submitted, Disputed, Released, Refunded }
struct Milestone { amount: i128, status: MilestoneStatus, proof_hash: Option<BytesN<32>>,
                   submitted_at: u64, dispute_reason: Option<BytesN<32>> }
struct Project { id: u64, license_id: u64, lab: Address, investor: Address, arbiter: Address,
                 challenge_period: u64, funded: bool, milestones: Vec<Milestone> }

fn __constructor(env, admin, token: Address, splitter: Address, treasury: Address, fee_bps: u32)
fn create_project(env, license_id, lab, investor, arbiter, amounts: Vec<i128>, challenge_period: u64) -> u64  // lab.require_auth
fn fund(env, project_id)               // investor.require_auth; transfers the full amount to the contract
                                       // then calls splitter.mint_shares(license_id, investor, total)
fn submit_milestone(env, project_id, index: u32, proof_hash: BytesN<32>)   // lab; Pending -> Submitted
fn dispute(env, project_id, index: u32, reason_hash: BytesN<32>)           // investor; only during the window
fn release(env, project_id, index: u32)    // anyone; Submitted + window over -> Released
                                           // pays the lab (amount - fee) and the treasury (fee)
fn resolve(env, project_id, index: u32, approve: bool)  // arbiter; Disputed -> Released or Refunded (to investor)
fn cancel(env, project_id)                 // investor + lab; refunds the Pending milestones
fn get_project(env, project_id) -> Project
fn list_projects_by_license(env, license_id) -> Vec<u64>
```

Security rules to test: milestones released **in order**, no double release,
no dispute after the window, only the arbiter resolves, total outflows never
exceed the deposit.

### 3.3 `royalty_splitter` (royalties + shares)

Principle: for each licence, fixed parts (university, inventors) and an
"investors" part shared **pro rata to the shares held**. We use a **per-share
accumulator** ("dividends" pattern): constant cost whatever the number of
holders, and everyone withdraws on demand (*pull*).

Storage: `Admin`, `Token`, `Treasury`, `FeeBps`, `Minter` (= escrow),
`Allowed(Address) -> bool` (KYC allowlist),
`Config(u64) -> SplitConfig`, `TotalShares(u64)`, `Shares(u64, Address)`,
`AccPerShare(u64)` (× 1e12), `Debt(u64, Address)`, `Claimable(u64, Address)`.

```rust
struct Beneficiary { addr: Address, bps: u32 }
struct SplitConfig { fixed: Vec<Beneficiary> /* university, inventors */, investors_bps: u32 }  // sum = 10,000

fn __constructor(env, admin, token, treasury, fee_bps: u32)
fn set_minter(env, minter: Address)                     // admin (escrow address)
fn set_allowed(env, who: Address, allowed: bool)        // admin = "KYC approved"
fn configure(env, license_id, config: SplitConfig)      // licence owner, only once
fn mint_shares(env, license_id, to: Address, amount: i128)    // minter; `to` must be allowlisted
fn transfer_shares(env, license_id, from, to, amount)  // from.require_auth; from and to allowlisted; settles earnings first
fn clawback(env, license_id, from: Address, amount: i128)     // admin
fn pay_royalty(env, license_id, payer: Address, amount: i128) // payer.require_auth; fee -> treasury;
                                                              // fixed parts -> Claimable; investors' part -> AccPerShare
fn claimable(env, license_id, who: Address) -> i128
fn claim(env, license_id, who: Address) -> i128              // who.require_auth; transfers the EURC
fn shares_of(env, license_id, who: Address) -> i128
fn total_shares(env, license_id) -> i128
```

Edge case: if `TotalShares == 0` when a royalty is paid, the investors' part
goes to the licence owner.

## 4. Front-end

Stack: React 18 + Vite + TypeScript, Tailwind, `@stellar/stellar-sdk`,
`@creit.tech/stellar-wallets-kit`, TS bindings generated for the 3 contracts.

| Screen | Role | Content |
|---|---|---|
| Home / Marketplace | Everyone | List of licences, amount raised, milestones reached |
| List a licence | Lab | 3-step form: details, terms, dossier (hash computed in the browser) → `mint` + `configure` + `create_project` |
| Licence page | Everyone | Terms, fingerprint, milestone timeline, royalty split, stellar.expert links |
| Fund | Investor | "Fund X EURC" button → `fund` |
| Lab dashboard | Lab | Submit a proof, see funds received |
| Investor dashboard | Investor | Shares held, dispute a milestone, royalties to withdraw |
| Pay a royalty | Licensee | `pay_royalty` |
| Admin / Arbiter | Platform | KYC allowlist, institutions, dispute resolution |

**Demo mode**: a role picker (Lab / Fund / Licensee / Arbiter) that signs with
4 pre-funded testnet accounts, to run the demo without switching Freighter
accounts. Freighter stays available in normal mode. The demo keys are
**testnet only**, in `.env.local` (never committed).

UX principle: **zero crypto jargon** for the researcher ("List", "Receive the
funds", not "sign a transaction"). Every action shows a toast with the link to
the transaction.

## 7. Tests and quality

- Soroban unit tests for each function (happy path + every expected `panic`),
  with `env.mock_all_auths()` and a test EURC SAC
  (`register_stellar_asset_contract_v2`).
- One integration test that replays the demo scenario **exactly**.
- Before the demo: `seed-demo.sh` dry-run at least 3 times.

## 8. Risks and mitigations

| Risk | Mitigation |
|---|---|
| Testnet RPC slow or down during the demo | Backup video + pre-seeded state |
| Unstable venue Wi-Fi | 4G hotspot ready |
| Challenge window too long for the demo | 60 s `challenge_period` for the demo project |
| No official testnet EURC available | Test `EURC` asset issued by us (told honestly to the jury) |
| Legal question from the jury | Prepared answer: "designed to be compliant, legal opinion in phase 2" |
| Not enough time on the front-end | Priority: listing → funding → milestone → royalty; the rest is optional |
